# Flowboard — Kanban (Go + PostgreSQL + React/TS)

```
backend/   Go, Clean Architecture: chi (HTTP), uber/fx (DI), PostgreSQL (pgx + goose),
           JWT (golang-jwt) + Redis (refresh-токени), OpenSearch (пошук карток), RustFS/S3 (аватарки)
frontend/  Vite + React + TypeScript + react-router + i18next: лендінг "/", вхід/реєстрація,
           проєкти "/projects/:id", налаштування "/settings"
```

## Архітектура бекенду

Залежності спрямовані лише всередину: `transport → usecase → domain`, адаптери реалізують порти use case-ів.

```
backend/
  cmd/server/main.go           точка входу: app.New().Run()
  internal/
    domain/                    сутності (User, Project, Column, Card…) і бізнес-помилки; без залежностей
    usecase/                   бізнес-логіка; кожен пакет оголошує свої порти (інтерфейси)
      auth/                      реєстрація, вхід, JWT-сесії (access + refresh)
      user/                      користувачі, аватарки
      project/                   проєкти й учасники
      board/                     колонки, картки, пошук
    adapter/                   реалізації портів
      postgres/                  репозиторії, транзакції, міграції goose (migrations/*.sql), демо-дані
      jwttoken/                  випуск і перевірка access-токенів (HS256)
      redisstore/                refresh-токени, denylist access-токенів, pub/sub дошок, присутність, журнали Yjs
      searchindex/               індекс карток в OpenSearch (edge n-gram, пошук за початком слова)
      s3store/                   аватарки в RustFS через AWS SDK v2
      bcrypthash/                хешування паролів
    transport/httpapi/         chi-роутер, middleware, DTO, обробники по модулях, WebSocket-хаб (realtime.go)
    config/                    налаштування з оточення та ../.env
    app/                       composition root: збирає всі fx-модулі
```

Кожен пакет експортує свій `fx.Module`. Адаптер прив'язує себе до портів, наприклад
`func(r *CardRepo) board.Cards { return r }`. HTTP-обробники додаються в групу `routes`,
і сервер монтує їх усі. Щоб замінити реалізацію, наприклад пошук, достатньо підключити інший модуль в `internal/app`.

Postgres — джерело правди. OpenSearch лише повертає id карток, що відповідають запиту.
Сортування, фільтри й курсорна пагінація виконуються в Postgres. Під час старту індекс звіряється
з базою і перебудовується, якщо кількість документів не збігається.

## Запуск

Спершу підніміть інфраструктуру: `make infra-up` (див. нижче). Бекенд бере паролі з того ж `.env`.

**Розробка** (два термінали):
```bash
make dev-backend    # API на :8080
make dev-frontend   # http://localhost:5173 (проксі /api -> :8080)
```

**Продакшн** (один бінарник віддає і API, і SPA):
```bash
make run            # http://localhost:8080
```

При першому запуску створюються демо-дані: 2 проєкти (KAN, MOB) і 5 користувачів.
Вхід: `demo@example.com` / `demo1234`. Демо-користувач — owner організації «Flowboard Inc.» (проєкт KAN)
і admin «Mobile Studio» (проєкт MOB, owner — Olena).
Також `olena@`, `andrii@`, `maria@`, `taras@example.com` з тим самим паролем.
`taras` не входить у жодну організацію — зручно перевірити запрошення. Для `new.hire@example.com`
вже є запрошення, яке спрацює, щойно хтось зареєструється з цим email.

Схема Postgres створюється міграціями goose під час старту. Міграція `00003` переносить наявні проєкти в організації:
кожен власник проєктів отримує організацію «<ім'я>'s workspace» з цими проєктами та їхніми учасниками. Демо-дані (англійською) додаються лише в порожню базу. Дані зі старої SQLite (`backend/kanban.db`)
не переносяться, тому файл можна видалити.
У демо-проєкті KAN 48 карток у першій колонці — щоб було видно нескінченний скрол.

## Інфраструктура (Docker)

`compose.yaml` піднімає PostgreSQL, Redis, OpenSearch, RustFS і Redpanda. Дані для входу лежать у `.env`, адреси й рядки підключення — у [credentials.md](credentials.md).
```bash
make infra-up       # docker compose up -d
make infra-down     # docker compose down
```
Бекенд використовує PostgreSQL, Redis, OpenSearch і RustFS. Redpanda поки не використовується.

## Можливості
- **Організації.** Створити може будь-хто, людина може бути в кількох організаціях. Ролі:

  | | owner | admin | member |
  |---|---|---|---|
  | запрошувати людей | ✓ (будь-яка роль) | ✓ (admin/member) | |
  | видаляти людей | ✓ | лише member | |
  | змінювати ролі | ✓ | | |
  | створювати проєкти, перейменовувати | ✓ | ✓ | |
  | видалити організацію | ✓ | | |

  Запрошення йде за email: зареєстрована людина приєднується одразу, решта — під час реєстрації.
  Останнього owner не можна понизити чи видалити. Хто вийшов або кого видалили, втрачає доступ до всіх
  проєктів організації, а проєкти, якими він володів, переходять до owner-а.
- **Проєкти** належать організації, у кожного своя дошка і ключ задач (`KAN-1`, `MOB-3`). Учасників у
  проєкт додає його власник, але лише з учасників організації. Виконавцем може бути лише учасник проєкту.
- **Головна `/home`** — статистика (організації, проєкти, призначені мені, термінові, створені мною),
  «Мої задачі», організації та проєкти. Залогінений користувач з `/`, `/login` і `/register` потрапляє сюди.
- **Спільна робота в реальному часі.** Деталі — у розділі «Реальний час» нижче:
  - аватарки тих, хто зараз на дошці, яскраві з зеленим кільцем, решта приглушені;
  - курсори колег у стилі Figma з іменами;
  - коли колега відкриває задачу, його курсор «влітає» в картку й стає аватаркою;
  - назва й опис задачі редагуються разом, з кольоровими кареткою інших людей;
  - під час перетягування картки інші бачать її «привид»;
  - будь-які зміни карток, колонок і учасників одразу з'являються в усіх.
- **Опис задачі — редактор у стилі Notion** (TipTap):
  - слеш-меню `/` з блоками (заголовки, списки, to-do, цитата, код, роздільник);
  - markdown-скорочення (`# `, `- `, `[ ] `, `> `, ``` ``` ```);
  - плаваюча панель форматування для виділеного тексту.

  У базі опис зберігається як markdown. Для наявної задачі окремої кнопки «Зберегти» немає:
  зміни зберігаються автоматично.
- **Файли в задачах** (до 50 МБ кожен, до 50 на задачу, зберігаються в RustFS). На картці — скріпка з
  кількістю файлів і обкладинка: мініатюра першого зображення або кадр першого відео. У вікні задачі —
  сітка файлів із превʼю, перегляд на весь екран, завантаження перетягуванням. Тип визначається за вмістом;
  мініатюри зображень (480 px, JPEG) генерує сервер. Відео віддаються з підтримкою Range (перемотування),
  а все, що не зображення і не відео, — лише як завантаження (`Content-Disposition: attachment`, `nosniff`,
  `sandbox`), тож HTML чи SVG з файлу не виконаються на нашому домені. Посилання на файли підписані HMAC
  і діють 1–2 доби.
- Видалити картку може автор або власник проєкту; видалити/перейменувати проєкт — лише власник
- Власні колонки: власник додає, перейменовує (подвійний клік або меню ⋯), переставляє й видаляє колонки
  (картки видаленої колонки переносяться в обрану)
- Нескінченний скрол: кожна колонка підвантажує картки сторінками по 20 (курсорна пагінація);
  пошук (OpenSearch: ключ, назва, опис, за початком слова) і фільтри по людях виконуються на сервері
- Аватарки: клік по своїй аватарці у верхній панелі → завантажити/змінити/видалити фото.
  Браузер обрізає фото до квадрата 256×256, сервер перевіряє тип (PNG/JPEG/WebP/GIF, до 5 МБ)
  і зберігає його в RustFS. Віддається через підписаний URL `/api/users/{id}/avatar?v=…&sig=…` з кешем «назавжди»
- Дизайн у стилі Liquid Glass (backdrop-filter, напівпрозорі шари) у світлій і темній темах
- Інтерфейс трьома мовами: англійська, українська, німецька (`frontend/src/i18n/`, i18next).
  `en.ts` еталонний, і TypeScript вимагає, щоб `uk.ts` і `de.ts` мали всі ті самі ключі.
  Бекенд, логи й демо-дані англійською
- Налаштування (`/settings`, посилання внизу сайдбару або клік по аватарці): мова (автоматично або
  обрана) і тема (автоматично, світла, темна). Зберігаються в акаунті (`users.language`, `users.theme`),
  тому діють на всіх пристроях. Автоматична мова — перша з мов браузера, яку ми підтримуємо, інакше англійська.
  Автоматична тема йде за системною. Без входу вибір зберігається лише в цьому браузері
- Помилки API: `{"error": "<English message>", "code": "<code>"}`. Фронтенд показує переклад
  `errors.<code>`. Каталог кодів — `backend/internal/domain/catalog.go`

## Реальний час

Один WebSocket на відкриту дошку: `GET /api/ws`. Першим повідомленням клієнт надсилає
`{type: "auth", token, projectId}`, бо браузер не дає поставити заголовок `Authorization` на WebSocket.
Чужі Origin відхиляються ще під час рукостискання.

- **Розсилка.** Повідомлення ходять через Redis pub/sub (канали `board:<projectId>`), тож кілька
  екземплярів бекенду бачать одне одного.
- **Події.** Після кожної зміни через REST use case публікує доменну подію (`card.created/updated/moved/deleted`,
  `columns.changed`, `members.changed`), а хаб розсилає її як DTO. Подія переміщення містить нових сусідів картки,
  щоб клієнт поставив її в правильне місце навіть при частково завантаженій колонці.
- **Присутність.** Хеш `presence:<projectId>` з TTL на кожне поле (`HEXPIRE`, Redis 7.4+) і серцебиттям
  раз на 20 с. Якщо екземпляр сервера впаде, його з'єднання зникнуть самі.
- **Курсори.** Курсор передається відносно картки або колонки під ним (`{kind, id, fx, fy}`), а не в пікселях.
  Тому він потрапляє в те саме місце при іншій ширині екрана й прокрутці. Клієнт надсилає позицію не частіше
  ніж раз на 40 мс (остання позиція надсилається завжди), сервер обмежує частоту ще й зі свого боку.
- **Канал користувача.** Кожна вкладка після входу відкриває ще одне з'єднання з `projectId: 0`, підписане
  на `user:<id>`. Через нього людина одразу дізнається, що її додали чи видалили з організації або проєкту,
  змінили роль, щось перейменували чи видалили:
  - сайдбар оновлюється, з'являється повідомлення;
  - зі сторінки, до якої більше немає доступу, переводить на головну;
  - сервер закриває її WebSocket до дошки (код 1008 «access revoked») і не пускає назад.

  Ті, хто дивиться на сторінку організації, бачать зміни учасників і ролей одразу.
- **Хто зробив зміну.** REST-запити несуть `X-Realtime-Conn` — id з'єднання вкладки. Подія повертається
  з `origin`, і пропускає її лише вкладка-автор (інші вкладки того ж користувача її застосовують).
- **Спільне редагування** через Yjs (CRDT). Сервер Yjs не розбирає, а лише зберігає нумерований журнал
  оновлень у `ydoc:<cardId>`:
  - перший, хто відкриє задачу, отримує право засіяти документ з markdown у Postgres (`SETNX`);
  - решта отримують журнал і живі оновлення;
  - клієнт час від часу стискає журнал у знімок (Lua, атомарно);
  - журнал живе годину після останньої зміни;
  - джерело правди — markdown у Postgres, його автоматично зберігає той, хто редагує.



- `login`, `register` і `refresh` повертають `{user, accessToken, expiresAt}` і ставлять cookie `refresh_token`
  (`HttpOnly`, `SameSite=Strict`, `Path=/api/auth`, 30 днів).
- **Access-токен** — JWT HS256 на 15 хвилин (`iss`, `aud`, `sub`, `exp`, `jti`). Фронтенд тримає його лише в
  пам'яті й надсилає як `Authorization: Bearer …`. Решта API приймає тільки цей заголовок, cookie ігнорує,
  тож CSRF для API неможливий.
- **Refresh-токен** — випадковий рядок, у Redis зберігається лише його SHA-256. При кожному `/auth/refresh` він
  міняється на новий. Якщо хтось пред'явить уже використаний токен, анулюється вся сесія (її «родина»).
  Виняток — 30 секунд після ротації, щоб дві вкладки, що оновлюються одночасно, не розлогінили одна одну.
- **Вихід** відкликає refresh-токен, а `jti` access-токена кладе в denylist у Redis до кінця його життя,
  тому токен перестає діяти одразу.
- Фронтенд оновлює токен сам: заздалегідь, коли до кінця лишається менше 30 секунд, або один раз після 401.
  Паралельні запити чекають одне спільне оновлення. Після перезавантаження сторінки сесія відновлюється
  через `/auth/refresh`.
- Помилки: `token_expired` (час оновити токен), `token_invalid`, `session_invalid` (refresh-токен недійсний),
  `not_authenticated`.
